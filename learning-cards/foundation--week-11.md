## 原教材重點
- 規劃 Tag、量測、警報及操作資料表，使用參數化查詢與明確交易邊界，設計日期區間報表及唯讀資料 API。
- 完成資料表欄位表、每日用電／運轉／警報統計規格，並設計 latest、history、alarms 三個 API 的請求、回應、分頁與錯誤案例。
- kW 是功率，kWh 是累積電量；用量計算要處理表計歸零、換表與缺值。此站沒有運行中的資料庫、報表產生器或 API。
- 設計 TagDefinition、Measurement、AlarmEvent 三張表；分開記錄定義、量測與事件。
- 報表：日期區間、設備、用電量／運轉時間／警報次數；寫出計算口徑與缺值處理。
- API 規格示例：GET /api/tags/latest、GET /api/tags/history、GET /api/alarms；這些網址不在本網站執行。
- 回應包含 TagId、Value、Unit、Quality、SourceTime；歷史查詢加入 from、to、page、pageSize，限制範圍並定義錯誤回應。

## 常見問題
### 這一課應先掌握什麼？
規劃 Tag、量測、警報及操作資料表，使用參數化查詢與明確交易邊界，設計日期區間報表及唯讀資料 API。

### C# 整合服務在本架構的責任為何？
採集、驗證、轉換及透過明確介面交換資料。服務應有清楚責任邊界，現場控制仍由對應控制層負責。

### Service 與 Repository 分工的目的為何？
分開處理流程規則與資料存取。必要的分工可降低變更影響，但不需為簡單工具增加過多層次。

## 記憶卡
- 問：外部採集失敗時，較好的重試設計為何？
  答：有逾時、間隔、上限與錯誤紀錄。受控重試能避免阻塞或對來源造成額外負荷。
- 問：唯讀 API 查詢大量歷史時，應規劃什麼？
  答：時間範圍、分頁、排序與錯誤回應。查詢契約應同時考量資料意義、效能與權限。
- 問：從瀏覽器練習通過，能否宣稱 C# 服務已上線？
  答：還需實際執行環境與整合驗證。教材模擬與真實服務是不同驗證層次。
